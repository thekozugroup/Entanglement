# Direct daemon package-loading review

The prior **Medium availability finding remains closed on Linux** for candidate `42bb9a3360ce2b4d5bcf2268dfa5a76bc6d6247e`. The optimized daemon rejected six invalid packages through RPC and six through configured startup. Both entry points subsequently loaded the repaired signed package and returned the expected result from a fresh invocation. The frozen Linux archive had SHA-256 `20072dbc38c0fc0c8c67df92933dda5224d4ba1e4e82163c80597f438f4df1cf`. I extracted its CLI and daemon into a disposable test directory, verified each against the release manifest and rechecked the binaries after execution. During each RPC refusal, the test checked that the plugin had not entered the live registry. The six configured startup attempts exited unsuccessfully within the test deadline. The output receipt contains the tested conditions and outcomes. [Archive manifest](linux-archive.json) · [Observed results](loader-boundary-linux.json)

The kernel reads the manifest, component and detached signature through a shared reader. On Unix it opens the final path component with `O_NOFOLLOW | O_NONBLOCK`, checks regular-file type and length on that open descriptor, and limits the subsequent read to one byte above the configured cap. The kernel then verifies the package signature. The exact-source workspace suite passed both named loader regressions.
