## Dispatch, authorization and request lifetime

- The local daemon calls the refresh-aware dispatcher for an ordinary one-shot request. A failed **placement** can request one inventory refresh under `None` or `TrustedExecutor`. Data has not been passed to an executor at this point. After a usable authenticated report, the dispatcher repeats the original plugin, hardware and trust selection once and reserves the selected worker. Time spent awaiting inventory reduces the original execution budget. Signed semantic/replica protocols, streaming, and transport/application errors keep their existing execution paths. A worker rejection or ambiguous delivery has no path back to the refresh branch. [Daemon RPC entry](../../../../../crates/entangle-bin/src/methods.rs) · [Dispatcher](../../../../../crates/entangle-scheduler/src/dispatcher.rs)
- Before this freeze, candidate 8e07cc25 returned a placement miss when an empty trusted-executor allowlist refused a legacy local fallback. That candidate failed its ordinary workspace suite. The corrected fallback returns the original typed integrity error `ENTANGLE-E0303`; an empty allowlist skips the refresh hook. The original test, dedicated no-transport refusal, and the refresh-aware path with a counted hook cover the correction. Both outcomes denied execution. [Previous failed suite](../candidate-8e07cc25/iteration-verdict.md) · [Dispatcher regressions](../../../../../crates/entangle-scheduler/tests/dispatcher.rs)
- The extra query sends the existing capability request. Its candidates come from explicitly configured peer identities; a trusted-executor allowlist narrows that set. The submitter checks the current trusted route before queueing, and the existing dispatch lookup checks the concrete descriptor/public-key association before an Iroh exchange. The worker checks the authenticated submitter against the persisted trust store before handling capabilities or jobs. A sighting, participant-specified ID or incompatible report cannot authorize execution. The final placement still validates capability freshness and requested resources. [Inventory collector](../../../../../crates/entangle-bin/src/capabilities.rs) · [Worker fit](../../../../../crates/entangle-scheduler/src/worker.rs) · [Authenticated exchange](../../../../../crates/entangle-scheduler/src/remote.rs) · [Route authorization](../../../../../crates/entangle-bin/src/remote/routes.rs)
- The normal 15-second lane and the expedited lane share daemon shutdown. Each runs at most eight simultaneous probes. Demand waves are separated by two seconds; demand probes have a two-second timeout and callers have at most 2.5 seconds within their task budget. Waiting callers share route checks and queries for the same peer, and a cancelled waiter can be discarded before a new probe. Completion versioning prevents an older periodic result replacing a newer demand result. In an early development draft, periodic completion could discard a demand reservation while a route check was still outstanding. The frozen code gives only expedited queries a reference to the demand completion state. A usable result can wake the caller even when another selected peer is silent. [Polling and focused regressions](../../../../../crates/entangle-bin/src/capabilities.rs)
- Four new, mutually trusted two-daemon clusters each ran an ordinary signed guest after the previously empty worker hot-loaded it. All four first submissions succeeded on the correct worker in 0.0914s median and 0.1057s maximum, with zero client retries. The archived baseline needed a subsequent periodic read in all four clusters, with eventual median 15.0305s. Four concurrent valid nonces per cluster each executed once. Six concurrent absent submissions produced 1 additional inventory read(s) and zero guest executions. A genuine guest InvalidInput error counted once. Revocation yielded zero worker executions, and a new authorized submission executed once after trust was restored. The job never executed locally. Each worker's empty loopback model catalog independently exposed authenticated inventory read events. Both runs used the same Linux x86_64 host and matched RPC fixtures under ordinary mixed host load. The timings measure first-job discovery. They do not establish saturated throughput, quiet-machine latency or physical-network performance. ## Rust test outcome reporting

The runner sends exact test names to a signed component under a specified remote peer allowlist and checks the returned executor. It compares lists of tests and ignores across selected workers. The change retains the distinction between a listing-time ignore with no attempt and a target-reported ignore after execution. A completed result needs one selected test, one matching libtest summary, a coherent exit status, and counts that account for that one test. A subsequent ignore cannot erase a prior failure or error; a later pass preserves the original attempt record. The independently run parser tests covered malformed/multiple summaries, panic-abort reporting, embedded header text, runtime ignores and retries. A trusted executor and signed harness remain assumptions for the content of stdout/stderr. An observed WASI ignore remains distinct from native test coverage. ## Evidence and residual bounds

Three consecutive ordinary, default-parallel runs of the frozen workspace each passed 783 tests and reported 29 ignored tests. The earlier publisher, loader and peer-trust dispositions apply to the unchanged source controls listed above. A fresh, isolated publisher-compromise rehearsal used the optimized Linux archive, rejected the retired publisher's package after unload and key removal, and restored correct behavior under a separately trusted key on the same running daemon. An internal disclosure notice was drafted and retained locally. A missing, revoked or unresponsive worker can still leave a job unplaced. LAN-only peers retain their ordinary inventory polling path. Short job budgets can expire before an inventory wave finishes. The existing 30-second ordinary Iroh exchange cap applies independently of a longer worker budget. This review covers the changed source and the recorded Linux controls. Separate physical hosts, upstream WAN/relay behavior, hosted CI/governance, independent external auditing and live disclosure response were outside these observations.
