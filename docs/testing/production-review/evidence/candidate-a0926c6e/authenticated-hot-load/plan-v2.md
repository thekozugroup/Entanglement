# Authenticated worker hot-load acceptance

Preregistered 27 November 2026 at 05:34 UTC before qualification measurements. Compare unchanged bb70a619 release ELF digests to the proposed isolated source built as optimized executables using the same Python runner, same Linux x86_64 host, ordinary owner Unix-socket JSON-RPC, one private IPv4 Iroh route, relay disabled, and one signed local hello-pong component. Both peers are explicitly trusted with their verified identity public keys. Only the worker trusts and loads the signed package. There are no external network dependencies.

Run four independently initialized two-node clusters per binary. Alternate logical roles between physical process labels A and B on each iteration. Time server-side worker package hot load after its first authenticated, genuinely empty plugin report. To observe that report without modifying the binary, give only the worker a private loopback model catalog which answers GET /v1/models with zero installed models. In RemoteTaskServer::respond the verified worker snapshots its loaded plugins, then calls the inference executor's catalog readiness check while constructing the authenticated capability response. Wait for the observed first catalog GET to finish and allow 100 ms for the response to arrive. Independently confirm that both local inventories begin empty. The coordinator has no plugins. Record exact elapsed monotonic time from successful worker plugin-load RPC response to completion of an ordinary allowlisted submission; retry at 0.5s intervals **only** after an unambiguous local placement -32000 “no live workers in pool”. Every timeout, remote rejection, ambiguous reply, incorrect worker or output is a failed trial without resubmission. Hard total deadline 24 seconds. Use the same nonce per trial across local placement misses; require exactly one successful execution via worker histogram, no coordinator Wasm execution and the exact expected output. Compare all four raw durations including outliers, median and maximum. Proposed behavior must finish each trial under 10 seconds.

After the measured first job, submit four distinct, simultaneous normal calls using the same selected worker. Each submission must return the matching nonce and the exact worker peer. Require four additional worker executions and no local executions. In the final cluster, submit a burst of six parallel requests for a valid but absent plugin name and require six local NoWorkers replies and zero new Wasm executions. Count inventory reads during the burst and following two seconds: at most two including any overlapping periodic poll. Send one worker-revoked case while the coordinator still has a recently valid inventory; require a dispatch refusal, no worker invocation and no local fallback, then re-trust and require a distinct correct result and exact execution count. Record readiness/read counts and elapsed timing; retain only disposable peer IDs and public digests, not secrets. Ordinary client submissions alone exercise the proposed trigger; the catalog adds no passive traffic of its own.

## First-call and error admission criteria

Added at 05:36 UTC, before running the proposed executable or learning any comparative result. Record the first submission's start/finish offsets, status and typed error, plus separate cold-path latency. The operator-facing pass requires **all four proposed first submissions**, each with unique nonce and no client retries, to complete on the expected trusted worker in under ten seconds. Subsequent local-only retries report eventual recovery if the first call missed and cannot satisfy the first-call criterion. Baseline misses are expected and individually retained.

The same signed hello fixture returns a guest InvalidInput error for a single invalid UTF-8 octet. After the valid parallel controls (outside the measured timing), send one ordinary operator invocation with that input in the fourth cluster, then require a worker-side execution error for that already loaded plugin, exactly one new worker Wasm invocation and no local invocation. The request is never retried by the test. The worker later successfully processes a fresh valid request after the separate revocation control. The baseline and proposed qualification use this same runner and plan.
