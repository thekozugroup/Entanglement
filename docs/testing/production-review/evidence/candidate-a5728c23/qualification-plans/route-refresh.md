# Preregistered Tailscale route refresh checks

Base is `296b427a3bb2d60615ea3c56b9779f97039c6e24`. Keep the existing Iroh key binding, live PeerStore trust and worker-side scheduler authorization. A tailnet status reply supplies an address for an operator-configured stable node ID and port. Keep the on-demand operation scoped to a peer already selected from compatible cached inventory, paired, explicitly mapped and missing a usable route. Exercise every transport configuration the change claims to support.

Record status command count and order, route snapshots, peer trust, capability-query count, job count, chosen peer, exact payload bytes, source revision and authenticated test identities. Use bounded, disposable local fixtures controlled by event barriers. The positive and pairing controls should reuse the actual signed one-shot CLI or daemon path with the known JSON Pointer fixture when a private tailnet fixture is available. A fake status parser check establishes address-selection behavior only.

1. **First request after a mapped worker becomes reachable.** Start with authenticated compatible inventory already cached, the mapped worker missing from the latest route snapshot and no installed coordinator copy. Provide the worker's online address in the next status result before the regular route poll. Pair both identities and load one valid signed plugin on the worker. Submit one ordinary allowlisted signed compute request. Require one demanded status query, selection of that worker, exact fresh expected bytes, one worker job, zero coordinator jobs and use of the operator's configured public key and port. Record that the regular route poll was held for the test. The existing cached inventory should incur zero demand capability requests.
2. **Pairing remains necessary.** Repeat with the correct mapped address and the coordinator's trust absent or revoked. Require a normal placement or trust denial, no demand status call and zero capability queries or jobs for that peer. With the coordinator's trust present and the worker's reciprocal trust missing, retain compatible cached inventory from before the change and require the existing authenticated scheduler rejection and zero jobs. Keep publisher trust unchanged through these two cases.
3. **Disabled and unmapped features.** In the Iroh-only case, retain a valid tailnet mapping in config and expose a reachable worker in the status fixture. Require no new status command from demand and no tailnet route. With Tailscale enabled and the peer paired but absent from the configured mapping, expose that peer in status and require no tailnet route, extra demand status command, capability query or job. Check that an already usable static/LAN/tailnet route does not start another status command.
4. **Bounded and shared work.** Hold one status query in flight, overlap multiple user requests already placed on the same eligible peer with no route and include a live second waiter after cancelling the first. Require shared route status work within the defined rate/concurrency limit, normal dispatch policy for each remaining user request, and no repeated job execution. Verify repeated missing/offline routes respect the global cooldown and do not keep a new command loop alive. An ordinary idle capability poll, a healthy cached route, stream opening and relay lookup should leave the status command count unchanged outside their existing periodic polling. Use a hung or over-limit status fixture to establish the dispatch response deadline and the independently bounded status subprocess lifetime. Follow with a later healthy request to show waiters and queue capacity recover.
5. **Ordering and revocation.** Hold the status response until after a committed local revoke, then release it. Require fail-closed route consumption and zero capability publication or execution for the revoked peer. Race a regular poll with a demanded poll using ordered distinct valid snapshots. Require a single ordered publication path or a generation check so an obsolete snapshot cannot overwrite the newer address after the application has published it. In Tailscale-only mode, an offline or retired listener must keep its established supervisor/rebind rules. Withdraw transport state or shut down while a status query waits and require no subsequent retry of the user job and no unbounded background work. A demand signal by itself should never bind or activate a Tailscale-only endpoint.
6. **Existing dispatch constraints.** Exercise a job rejected before placement (such as an oversized request) and an already selected job whose transport fails. Neither should start a pre-wire route-demand status call or replay the job. Include a short-deadline request and confirm bounded waiting without expanding the permitted end-to-end budget. Keep prior deadline accounting and original denial semantics. Check that static and LAN dispatch, mixed-mode availability and current peer-trust decisions are preserved.

Record unsupported physical/private-tailnet runs as unexecuted. Keep the normalized proof separate from the frozen release evidence.
