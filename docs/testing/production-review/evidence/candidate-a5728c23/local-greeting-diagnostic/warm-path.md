# Ordinary local greeting path

The greeting fixture exports the ordinary `entangle:plugin` world. Both daemons parse a successful `compute/dispatch` request over the Unix socket, choose the locally loaded positive-resource candidate, invoke the compiled ordinary plugin and serialize the successful response. Between c19ef758 and a5728c23 the dispatcher, worker pool, placement algorithm and RPC client source remained unchanged. The RPC response change adds typed data when formatting an error. The runtime's new signed command identity is computed when loading a libtest world. Ordinary greeting calls still select `Exports::Plugin(_) => None` before creating the store; the libtest identity comparison and capture occur in the other branch. Remote transport error propagation and configured peer convergence operate outside this isolated submission. Source review found no new unconditional filesystem read, signature operation, worker lookup or lock acquisition on the successful local greeting. One plausible CPU-level effect is a different in-memory layout of the loaded handle or the release binary, even when the ordinary dispatch path performs the same logical work. Existing optimized metadata probes measured the `LoadedPlugin` handle at 144 bytes on c19, 208 on interim 296b and 136 on the optimized 4dd source used in the integrated candidate. The ordinary export variant retains its same pre-instantiated Wasmtime handle; only the libtest variant introduces a new shared pointer. The isolated size-change study’s local greeting confidence intervals included 1.0. These observations do not identify a cause for the integrated primary p95 change.
