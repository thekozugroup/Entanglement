# Single-daemon local greeting diagnostic

Registered before sampling. The seven-route primary result is fixed at five passing routes. With four local clients the ratio of median p95 was 1.0682 and throughput was 0.9632; with one client the values were 1.0551 and 0.9550. Each used three paired comparisons. An older 296b/c19 diagnostic saw substantial identical-binary drift and a different candidate. This experiment asks whether the same daemon contrast is reproducible on the isolated local endpoint beyond the same-binary variation, at both concurrency levels. It is supplemental and does not change the seven-route grading.

Use the archived c19ef758 and a5728c23 daemon ELF files, verified against both archive manifests. Every arm starts a new daemon, uses the same disposable node identity, loads the same signed tier-1 hello-pong component, and dispatches solely to the local Unix socket with no configured remote workers. Use the same prebuilt Rust `entangle-rpc` client for all arms. It checks each actual peer ID and every output byte. The seven-route driver uses a two-thread Tokio client and a paired topology and cannot disable remote work. This diagnostic uses the retained current-thread Tokio client with one or four in-flight UDS callers, a single daemon, and no network workload. The inner timers exclude argument preparation, signing, startup and plugin loading. The daemon gets two Tokio and two Rayon threads.

Use eight independently randomized matched build pairs and eight interleaved a5728c23/a5728c23 controls. Group the schedule into eight four-arm blocks, each containing one pair of each kind. Balance baseline-first versus candidate-first 4:4 and control X-first versus Y-first 4:4, the order of the two kinds of pair 4:4, and one- versus four-client first 4:4. Both arms of each pair use the same concurrency order. Use Python's local random seed 572427 only for fixed order generation, and store the full sequence before the first arm. Use CPUs 0–1 for the common client and CPUs 2–3 for the daemon throughout, on the existing cgroup quota. Retain per-arm CPU affinity, daemon process CPU, cgroup throttling, independent load monitor, timings and cleanup. Keep all completed observations in their planned order; report any incomplete pair. Stop at 180 seconds elapsed from the first arm, on a real client/worker mismatch, or on a setup failure; do not re-run based on results.

Per arm and concurrency, perform 128 warmups followed by 1,024 timed requests. Every input uses the primary workload's `jobXXXXXXXX` format with distinct 8-digit hex indices per concurrency’s warmup and sample, 5-second timeout, 0.01 CPU cores, zero other resource floors and integrity none. The expected bytes are independently prepared as `Hello, <input>!`. The Rust client reports nearest-rank p50/p95, wall time, total rate and its CPU ticks. Report every pair’s ratios and the median paired p95 and throughput ratios with 95% fixed-seed paired bootstrap percentile intervals (10,000 resamples); report matching same-binary controls and median p50. Compare warm-local p95 to 1.05 and rate to 0.95 as original reference thresholds. A persistent adverse signal in this diagnostic requires the mixed-build p95 lower interval to exceed 1.05 and the paired control noise-adjusted ratio lower interval to exceed 1.0 at the same concurrency. Bootstrap matched four-arm blocks for that ratio of ratios. No unmeasured code-level cause or physical-host extrapolation.
