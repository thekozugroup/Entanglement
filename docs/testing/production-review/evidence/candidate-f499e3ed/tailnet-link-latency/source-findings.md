# Call path and cost

The new CLI arm on `MeshCmd::Tailnet { cmd: Some(..) }` calls the link implementation. It queries the built-in adapter once via `MeshTailscale::default().status().await`, then proceeds with local identity, configuration and paired-peer validation. The existing no-subcommand status listing retains its own original control path. The adapter invokes only the local `tailscale status --json` executable, waits up to five seconds and limits stdout to 16 MiB, killing its child on drop. The timeout applies to the subprocess read and wait. Configuration, identity and peer files have their own I/O costs; five seconds is not an end-to-end guarantee for the operator command. Startup and TOML/status parsing, peer and mapping scans, and an atomic update if necessary are operator costs.

The daemon-side source change factors the exact same Tailscale IP range predicate into the adapter crate. Existing route lookup, refresh timers, retry budgets and dispatch code are unchanged. A warm dispatch checks already-present route hints and current authorization. The existing demand status refresh runs when a trusted mapped route is missing, with a 750 ms request cap and coalescing; its periodic 30-second owner remains independent of CLI link calls. The new CLI function is not referenced from the daemon or scheduler. This establishes that the feature adds no new status polling or filesystem transaction on every existing job. A newly configured peer can add its intended route reconciliation and capability traffic after the daemon reads the configuration. Operator timings are not observations of per-job latency.

For a changed configuration the operator takes the nonblocking configuration writer lock, checks the current peer store, writes and syncs the replacement, rechecks the peer binding during the transaction, renames the temporary file and syncs the containing directory. The idempotent path still checks current visible status, trust and config under the lock, but skips replacement and file/directory durability syncs. Concurrent operator modifications report a busy writer rather than inducing an unbounded status-poll loop. Real elapsed time depends on status program, status size, current filesystem and durable write costs.
