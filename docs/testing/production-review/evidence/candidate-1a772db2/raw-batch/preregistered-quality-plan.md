# Pre-implementation test plan: Workload B dehaze

Drafted before the new implementation on 27 November 2026. This plan adds evidence for the requested capability; it does not alter the frozen 57-gate rubric, replace an existing acceptance condition, or claim that a small local test satisfies PERF-IMAGE. The exact command/input/output contract and supported formats must be recorded before generating expected outputs. If the implementation deliberately specifies a different color space or alpha policy, document that policy and freeze the fixture generator and corresponding checks before observing candidate results. Do not relax a failed numeric threshold after the fact; publish any revised protocol as a separately versioned run alongside the original.

## Fixed quality oracle

Use a standalone, deterministic Python/Pillow + NumPy fixture generator and analyzer, written independently of the plugin. Archive the generator, parameters, versions and SHA-256 of all inputs before invoking the candidate. Generate at least three 128×96 RGB clear reference scenes with gradients and nonuniform colored texture, no saturated pixels, and both low- and high-frequency detail. In a documented common color space generate hazy images independently using `I(x,c)=J(x,c)*t(x)+A(c)*(1-t(x))`, known atmospheric color A and bounded smoothly varying transmission t in [0.45, 0.80]. Do not supply A, t, J or expected output to the plugin. Include a separately generated already-clear, textured image. Use lossless PNG for these algorithm tests; decode the returned file independently and check exact dimensions, mode and finite 8-bit channels. If alpha support is advertised, include an RGBA fixture and assert alpha preservation independently.

On each hazy image calculate mean absolute RGB error relative to J before and after processing, in the same specified color space. Predeclared quality gates: aggregate post-process MAE at most 0.90× aggregate hazy MAE; at least two of three scenes improve by at least 5%; no individual scene's MAE worsens by more than 5% (handle zero denominators explicitly). On the clear control, require mean absolute change ≤2/255 and no more than 0.5% of channel samples newly clipped at 0 or 255. Include fixed references for orientation, channel order and nontrivial spatial texture. These are quantitative synthetic-scene checks, not proof of aesthetic quality across photographs. If a dehaze algorithm explicitly promises an exact documented transform, also implement that specification separately and check a tight independently derived pixel tolerance; do not import or call its production code in the oracle.

For actual RAW support, separately use at least two legally redistributable, pinned real camera RAW files from distinct cameras/sensor layouts where feasible. Record license, immutable source URL, file SHA-256, camera and format, and independently decode inputs and lossless output using a pinned external decoder. Assert decodability, orientation/dimensions/color interpretation as documented, finite pixel values and a nontrivial output; do not infer dehaze accuracy from a RAW photograph without a known clear reference. If RAW or a camera format is unsupported, record that as an actual limitation, not a successful RAW test.

## Input, resource and output boundaries

Before testing fix explicit published input byte cap, decoded dimension/pixel cap, supported formats, output size limit and timeout/memory budgets. Test the exact boundary and boundary+1 for each limit without allocating unbounded inputs; corrupt/truncated valid headers, empty input, unsupported formats and malformed options must produce bounded nonzero/typed errors, no valid-looking output and no daemon loss. Use otherwise-valid controls on both sides of each boundary so refusal is attributable to the tested limit. Exercise declared limits across local and remote paths. Do not claim compressed-size tests alone cover decoded-size limits.

For a disposable recursive directory, include nested paths, case-distinct names where supported, duplicate-content files, distinct files with identical basenames in different folders and a non-image file. Preserve an independently generated relative-path-to-input-SHA-256 manifest. Check reported success/failure against each input and map outputs to relative paths without basename collisions; decode every success and bind its bytes to its corresponding single-image invocation/reference. Check documented behavior for non-image and failed files, existing outputs and interrupted runs; require no reported success for failed items, and test any atomic-write/overwrite guarantee only if the implementation actually promises it. Verify source file hashes and directory contents after execution. Restrict all paths to a synthetic disposable directory and do not use credentials.

## Remote execution and identification

Retain all seven current catalog smoke workloads locally and through the empty coordinator (`plugins/smoke_test.py --two-node`). Add dehaze to the same reusable assertions instead of a parallel weaker harness. For each output record input SHA-256, decoded dimensions, output SHA-256, task identity, selected peer and result validation outcome. On two authenticated workers, perform directed per-peer runs with distinct inputs and the same independent image oracle; assert the actual selected peer, correct output association and byte-for-byte results against the directed local output where deterministic. Exercise `--raw` and `--output-file`, including exact bytes and separate diagnostics, and trusted-executor allowlists; invalid/untrusted peer must not execute and must not yield a purported success. For a three-worker small local smoke assert successful work was genuinely attributed to all three distinct worker identities, no duplicate or omitted inputs, and the coordinator hosts no executable plugin. Same-host workers demonstrate correctness and attribution only, not separate hardware, network bandwidth awareness or architecture speedup.

## Predeclared measurements and scoring boundaries

Freeze candidate commit/source ID, signed plugin/Wasm hash, CLI/daemon hashes, input manifest, oracle and harness before timed execution. Measure identical workload and output assertions for one worker and three workers, include warmups, at least three independent rotated-order trials and full latency distributions (p50/p95 plus total wall time); record concurrency, worker/host identities, hardware, CPU quotas, network routes, cache state, raw samples and resource use. Re-run correctness and placement validation for every timed output. Failed, missing and rejected outputs must be counted rather than silently dropped. Use a dedicated quiet window and record competing work; explicitly identify same-host capacity sharing and uncontrolled network.

A small synthetic/RAW sample can validate functionality and provide local engineering measurements but cannot satisfy Workload B's production criterion. `PERF-IMAGE` only passes for the architecture's actual 8,000 RAW photos distributed across three desktop nodes with ≥10× measured wall-clock speedup versus the same single-machine workload, including genuine placement/route evidence. Keep the originally defined workload and threshold. The existing PERF-BASELINE requires a previously approved comparable baseline and ≤5% regression, separately from scaling; do not approve a baseline retroactively. Preserve any slower results and uncertainty. Continue to score all 57 original checks independently; new image success does not confer platform, tailnet, governance, release, 70B, distributed-test or other unrelated passes.
